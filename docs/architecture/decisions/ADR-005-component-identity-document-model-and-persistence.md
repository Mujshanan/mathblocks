# ADR-005: Component identity, document model, and persistence

- **Status:** Accepted
- **Date:** 2026-11-20
- **Decision owners:** MathBlocks maintainers
- **Scope:** Stable document/component identity, framework-independent document structure, interchange serialization, and persistence boundaries
- **Related decisions:** ADR-001 (AnyWidget component architecture), ADR-002 (canonical mathematical expression representation), ADR-004 (state synchronization and component lifecycle)

## Context

MathBlocks components need stable identities and a portable representation that can be serialized, restored, copied, moved, and exchanged between host applications. The current AnyWidget state contract describes live synchronization for one component instance; it is not by itself a document format or a persistence system.

MathBlocks must define the mathematical UI document and its component records without becoming coupled to a notebook host, frontend framework, DOM layout, or a particular storage backend. The first version should establish a durable interchange contract without prematurely committing to a page editor or canvas.

## Decision

MathBlocks SHALL define a framework-independent, versioned document model containing an ordered collection of component records. It SHALL provide validated JSON serialization and deserialization for that model. Host applications own storage and persistence workflows.

### 1. Identity model

MathBlocks MUST distinguish the following identities and version markers:

- **document_id:** Stable identity of one logical MathBlocks document.
- **component_id:** Stable identity of one logical component instance within a document.
- **view_id:** Transient identity of a particular frontend view. It is not a persisted component identity.
- **revision:** A state/document update version used for synchronization or change tracking. It is not object identity.
- **expression identity:** Not required by the initial document contract. An application may introduce one through a separately defined contract if needed.

Document and component identifiers SHALL be opaque UUIDs generated by the Python/core boundary. Consumers MUST treat them as opaque strings and MUST NOT infer semantics from their format.

#### Identity lifecycle

1. Creating a document generates a new `document_id`.
2. Creating a component generates a new `component_id`.
3. Updating state, rerendering, reconnecting, saving, and restoring MUST preserve the existing identities.
4. Copying a document MUST generate a new `document_id` and new `component_id` values for every copied component.
5. Copying a component MUST generate a new `component_id`; the original and copy are distinct logical component instances.
6. Moving a component within a document MUST preserve its `component_id`. A move changes its position in the ordered collection, not its identity.
7. Deleting a component removes its record from the document. Implementations MUST NOT immediately recycle its identifier for a newly created component.
8. Importing a document as a new independent copy follows the copy rules. Restoring the same document follows the restore rules and preserves identities.

A host operation MUST make the distinction between copy and move explicit; MathBlocks MUST NOT infer a move from a remove-plus-insert sequence when identity intent is ambiguous.

### 2. Document structure

Version 1 SHALL represent a document as an ordered collection of component records, together with document metadata and schema information.

The order of records is meaningful and MUST be preserved by serialization and deserialization. This order is the document's logical component order; it does not imply page coordinates, columns, canvas positions, or a particular visual layout.

Version 1 does NOT define:
- Pages, page sizes, coordinates, or spatial positioning.
- Canvas, freeform placement, or layout constraints.
- Nested documents, groups, or container components.
- Cross-document references or attachments.

Hosts may present the ordered collection using their own layout. A future layout model requires a separate decision and versioned extension.

### 3. Canonical document envelope

The conceptual version-1 JSON envelope is:

```json
{
  "schema": "mathblocks.document",
  "version": 1,
  "document_id": "opaque-uuid",
  "metadata": {},
  "components": [
    {
      "component_id": "opaque-uuid",
      "type": "mathblocks.math",
      "schema_version": 1,
      "state": {}
    }
  ]
}
```

This is the architectural shape; the concrete Python types and JSON Schema are implementation deliverables.

Each component record contains:

- `component_id`: stable identity of this component instance.
- `type`: stable, namespaced component type identifier.
- `schema_version`: version of that component type's serialized state schema.
- `state`: component-owned JSON-compatible domain data.

The component type identifier MUST NOT depend on Python class names, import paths, frontend module names, or DOM/custom-element names. Renaming an implementation class or reorganizing frontend files MUST NOT silently change the persisted type identifier.

The document schema version and each component schema version are independent. The live AnyWidget state envelope's `schema_version`, `revision`, and `actor` are also separate contracts and MUST NOT be copied into persisted component identity fields merely because they are available at runtime.

### 4. Component registry and unknown components

MathBlocks SHALL provide a component registry that maps stable type identifiers to known component definitions. A registered definition is responsible for validating its state, identifying supported schema versions, and providing any required migrations and restoration behavior.

- The built-in registry contains MathBlocks component types.
- A host application MAY provide explicitly registered extensions.
- Persisted type identifiers MUST be resolved only through the registry; deserialization MUST NOT dynamically import arbitrary modules or execute code named by document content.
- Known components with supported schema versions are validated and restored.
- Known components with older supported versions are migrated through explicit, deterministic migrations.
- Unsupported or unknown component types MUST be preserved as their original serialized records when the record is structurally valid JSON and its identity/type envelope can be verified.
- Unknown or unsupported records MUST expose diagnostics to the host/application. They MUST NOT be silently dropped, replaced with empty components, or treated as understood content.
- A consumer that cannot safely verify the record's minimum structure MUST report a document-level diagnostic and fail or quarantine the affected record according to the documented deserialization result; it MUST NOT silently discard it.

Preserving an unknown record does not make it editable, renderable, or semantically understood. A host may display a placeholder and allow the record to be exported unchanged.

### 5. Serialization and deserialization

JSON is the canonical interchange format for MathBlocks documents.

Serialization MUST:
- Produce deterministic JSON for equivalent document state, including stable component ordering.
- Preserve document and component identities.
- Preserve component type identifiers and component schema versions.
- Preserve canonical mathematical expression data and original source metadata as defined by ADR-002.
- Include only persisted domain data and document metadata.
- Exclude frontend view identifiers, actor IDs, cursor/selection/focus/hover state, DOM objects, widget instances, callbacks, and other runtime-only values.
- Reject values that are not valid under the document/component JSON contract rather than silently coercing or dropping them.

Deserialization MUST:
- Validate the document envelope and schema version before restoring components.
- Validate component record structure and identity fields.
- Resolve known types through the explicit registry.
- Apply only declared component migrations.
- Preserve structurally valid unknown records and return diagnostics.
- Preserve record order and stable identities.
- Avoid executing code or loading arbitrary modules based on document content.

No Python pickle or equivalent executable object serialization is part of the public persistence/interchange contract.

### 6. Persistence boundary

MathBlocks owns:
- The document and component data models.
- Document/component identity rules.
- JSON serialization and deserialization.
- Validation, registry lookup, migration contracts, and diagnostics.

The host application owns:
- Reading and writing files.
- Autosave scheduling and recovery.
- Database schemas and transactions.
- Cloud storage, synchronization, permissions, and sharing.
- Application-level document history, backup, and retention.

MathBlocks MAY provide convenience APIs that serialize to or deserialize from JSON-compatible strings/objects. It MUST NOT require a particular filesystem, database, cloud provider, or host persistence service.

### 7. Relationship to live component state (ADR-004)

ADR-004 defines the live AnyWidget synchronization envelope for a component instance. ADR-005 defines a persisted document envelope. They serve different purposes:

- Live state synchronization carries revision and actor information needed to order updates among Python and frontend views.
- Persisted document records carry stable document/component identities, component type/schema versions, and domain state.
- Frontend-local interaction state and per-view actor identity are not persisted as document component data.
- Saving a document captures the accepted component domain state, not an arbitrary stale frontend snapshot.
- Restoring a document reconstructs components with the persisted identities and validated domain state; runtime views and actor IDs are newly established.

The implementation MUST define a deliberate conversion between the live component state payload and the persisted component record. It MUST NOT conflate the two envelopes or treat a live revision as a document identity.

## Alternatives considered

1. **A page/canvas document model in version 1.** Rejected: spatial layout is not required to establish portable component persistence and would prematurely couple the data model to a particular editor.
2. **Persisting Python/AnyWidget objects directly.** Rejected: host/runtime coupling, unsafe executable serialization, and poor interoperability.
3. **Dropping unknown component records.** Rejected: causes silent data loss when documents move between versions or hosts with different extension registries.
4. **Making MathBlocks own file/database/cloud persistence.** Rejected: storage policy belongs to the host application and differs across deployments.
5. **Treating copy and move as the same operation.** Rejected: copy creates a distinct logical instance, while move preserves the identity of the existing instance.

## Consequences

### Positive

- Documents can move between supported hosts without depending on a specific UI framework or storage backend.
- Component identity remains stable across edits, save/restore, and moves.
- Copy operations create independent logical component instances.
- Unknown components can survive round-trips through hosts that do not understand them.
- The initial model remains small and ordered, leaving spatial layout for a future decision.
- The live synchronization protocol remains distinct from persisted document interchange.

### Trade-offs

- Component registries and schema migrations require ongoing maintenance.
- Hosts must handle diagnostics and unknown-component placeholders.
- A deterministic JSON contract constrains component state to portable data.
- Layout and rich document composition require a future extension rather than being implicit in version 1.

## Acceptance criteria

- [ ] Framework-independent document and component record models exist.
- [ ] Document and component IDs are opaque and stable across updates and save/restore.
- [ ] Copying a document creates new document and component IDs.
- [ ] Copying a component creates a new component ID.
- [ ] Moving a component preserves its component ID.
- [ ] Version 1 preserves deterministic component order and defines no page/canvas layout.
- [ ] Document and component schema versions are independently validated.
- [ ] Stable component type identifiers are independent of implementation paths.
- [ ] Registry-based restoration and explicit migrations are supported.
- [ ] Structurally valid unknown component records survive deserialization/serialization with diagnostics.
- [ ] Invalid or unsafe records produce explicit diagnostics and are not silently discarded.
- [ ] JSON serialization is deterministic and excludes transient frontend/runtime state.
- [ ] No pickle or arbitrary dynamic imports are used for document restoration.
- [ ] Host storage and autosave responsibilities remain outside MathBlocks.
- [ ] Conversion between ADR-004 live state and persisted document records is explicit and tested.

## Deferred decisions

- Page, canvas, spatial layout, and responsive placement.
- Nested documents, groups, and container components.
- File formats beyond canonical JSON.
- Autosave, storage backends, cloud synchronization, and access control.
- Undo/redo, document history, and collaboration.
- Cross-document references and attachment storage.
- Expression-level identity and identity semantics for shared/reused expressions.
